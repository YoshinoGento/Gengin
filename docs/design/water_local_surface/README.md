# 試験農場：局所浸透と流れる水面（2026-11-27）

本編とセーブの既定は旧方式。試験場だけで、配水と描画を別々に選べる。以下は実行結果であり、楽しさの評価や出荷判定ではない。

## 試す

Release x64 をビルドし、ルートで `tools\start_water_trial.cmd compare C`。手前と奥にニンジン、短い分岐、開門から48固定ステップ（0.8秒）で停止する。
`G` はそのまま新旧描画、`F1/F2/F3` は水面／落水追加／飛沫追加、`I` は診断、`P` は進行。普通に掘るには引数なしで起動。1〜5で掘削・鍬・種・じょうろ・収穫、クリックまたは矢印とSpaceで作業。掘削を開口に再適用すると閉門。`L` は浸透方式を切り替え**農場をリセットする**。
自動比較は `tools\start_water_trial.cmd compare C classic`、旧計算は `tools\start_water_trial.cmd compare C shaded legacy`。10秒時点の診断は `tools\start_water_trial.cmd inspect`。

## 配水

水源補給→既存の辺移送→確定した残量から浸透を予約→競合する要求を水路ごとに比例縮小→土と水路に反映→成長更新。正本は FarmGrid。計算中の残量と要求配列は1ステップの作業用で、描画は差分を読み取るだけ。

給水可能な畝・同じか高い隣接水路の4辺だけを対象とする。単位 U はマス容量1を基準とするゲーム内単位。土壌水分1 Uは表示上100ポイント。各辺の接触長はこの盤面では等しく、水路残量は定断面の水深の代理で、実世界の水位ではない。
畝の希望量は「0.96までの余裕」と「基準浸透能力 × dt × 既存の土壌水分曲線 × min(1,隣接残量の和)」の小さい方。水路の残量比で希望量を分け、同じ水路を複数の畝が要求する場合は供給可能量で縮小する。競合で余った供給能力を別の水路に再配分する最適化はしない。単一ドナー選択を撤廃したのは**浸透**で、移送用の親木まで物理流体にしたわけではない。

- 新方式は4倍（1/15シミュレーション秒/更新）でも3作目品質は同じ。分岐47.20秒、一本道46.87 / 49.73秒。刻み幅変更時の到達時刻まで完全一致するわけではない。
- 2経路の各倍率で、掘削を逆順とし盤面を左右反転した等価水源と、各ステップの水量・水分・成長・累積移送、収穫結果を比較。4方向のドナーを複数の畝が取り合う小水量fixtureでも、負の残量と畝の上限超過なし。新方式4試行での水路収支の最大絶対誤差は 8.95×10⁻⁸ U 未満。任意形状での順序独立性の証明ではない。環状経路の合流は移送の親がまだ探索順で決まる（対称fixtureで11、鏡の対応先は13）。
- 水路残量の式は「開始在庫＋水源流入－土壌流入」。土は別帳簿で「開始水分＋実流入－成長時の実消費－収穫時の実減少」。短い分岐・1倍の6収穫で、土壌流入3.90163 U、作物消費1.71030 U、収穫控除1.50000 U。控除は `FarmToolBehavior.cpp` の共通定数0.25を残量でクランプしたもので、成長消費と別。設計意図を裏付ける資料は確認できず、農学上必須という根拠もない。今回は比較条件を変えず、試験CSVに実減少量を追加した。
- 掘削5回で両畝に届く分岐の利点は残り、自然でなかった大きな品質差はほぼ消えた。長い一本道も同等品質になり得る。これを失敗とみなし係数で差を戻すことには反対。次は給水範囲・工事の手間・余った作業時間を見て人が経路を選ぶか、また過湿や収穫控除が意味のある選択になっているかを調べる。30日大会における有利不利は未検証。

## 描画

[旧描画・通常距離](classic.jpg) / [新描画・通常距離](shaded.jpg)。両画像ともRelease、通常見下ろし、同じ照明、同じ開門手順、局所浸透、C、0.8秒。診断ラベルは非表示。旧と新で変えたのは描画で、計算方式を見た目と同時に切り替えた比較ではない。

- 水深の代理値で色と透過率を変え、不透明な底を先に描く。水路の実移送から向き・演出強度を得て、細長いうねりを進める。単位時間あたり移送量は流速(m/s)ではない。乾燥・閉門自体ではなく実移送が止まれば移流は止まる。池の深度は定数で、揺らぎは風の近似。屈折、反射像、水深バッファからの厚み復元は行わない。
- 波の傾きから局所法線を作り、視線・光源との関係で反射とハイライトを出す。Normal MapテクスチャやDynamic Flow Mapテクスチャは増やさない。流向のある模様という目的には賛成だが、20マスの試作で動的テクスチャの生成・同期まで必要とは判断しなかった。
- 落水は、開口の実メッシュ幅×流入強度の平方根で幅を決め、厚みは水源側の設定水深と上下水面の落差で制限する。表と両側面からなる帯、着水側の短い波紋、最大10個のCPU立体滴。開口の流入が止まれば新規の帯は発生せず、すでに落下中の帯と滴は寿命で消える。水量を再加算しない。
- 土の湿りは既存の連続的な土色を使用。水分率・開口状態・流入・作物消費は診断モードのみ。見た目の限界は、広い池の模様の反復、曲がり・分岐でのタイル単位の向きの切り替わり、飛沫の小ささ。水滴を増殖させる前に曲がりに沿う局所座標・隣接流向の補間と、落水着地点のコントラストを試す。

同一PC・1280×720クライアント、各1実行、16サンプルを捨て64サンプル、P95はnearest rank。計測は不透明地形の後、水面開始から落水・飛沫の描画終了まで。GPU query実行時は画面上の診断ラベル整理前だが、それらの描画は計測**後**。全フレーム時間や広い農場の性能ではない。PS呼び出し数は重複塗りの負荷の参考値で、ユニーク被覆画素数がないためOverdraw倍率は分からない。アダプター/ドライバと電力状態を含む他機種での再現、PIXによる面別の可視化は未実施。[旧GPUログ](gpu-classic.csv) / [新GPUログ](gpu-shaded.csv)

追試はPowerShellで `$env:SUIRO_WATER_TRIAL_PROFILE='1'`、上のcompare起動後は停止状態を変えずに待つ。各モードを別プロセスで起動し、`%TEMP%\SuiroWaterTrial\gpu-<variant>-<pid>.csv` に64行出たことを確認する。
CPU試験（MSVC x64 /O2、二畝、各1800tick、1回）では、局所灌漑を含むSystem::Stepが旧/新表示時平均4.13 / 4.59 µs、観測・効果頂点生成が0.93 / 2.07 µs。前者の計算経路は同じで差を性能差とは解釈しない。CPU描画提出、UI、ゲーム全体はこの測定には含まない。

新規描画PSOは試験シーン所有のComPtr。静的メッシュ・既存CBとRoot Signatureを共有、RT0だけBlend、法線RTとDepthへの書き込みなし。色・深度をSRVとして同時に読まないため新規の画像BarrierやDescriptorは不要。計測時のみQuery Heap・COPY_DESTのReadback・専用Fenceを持ち、完了したサンプルだけMapする。水面テクスチャの追加なし。正確なVRAM使用量や常駐量は未計測。生の配列ポインタは保持せず、形状は固定配列（新方式は最大372頂点、容量420）。描画が農場の値を書き換えないことを照合した。既存ParticleManagerのResource確保／Map失敗経路はこの試作に使っていないため未修正、配布前の別修正。共有エンジン全体やDX12 Debug Layer/GPU Validationの監査完了を意味しない。

## 変更箇所と再現

- `FarmIrrigationSystem.{h,cpp}`：本編既定はPathStrengthのまま、LocalContactのみ浸透を2パスにする。従来の到達可能性や単一水路を返す照会は実流量ではない。試験診断には実績のGetLastTileFlowsを使う。
- `WaterTrialSystem.{h,cpp}`：方式選択・収穫控除実測。`WaterTrialFlowView.h`：辺移送の表示信号、帯・波紋・滴。`WaterTrialScene.{h,cpp}`：操作、比較、計測を配線。`tools/start_water_trial.cmd`：比較起動。
- `FarmRenderer.{h,cpp}`、`Object3d.{h,cpp}`、`Model.h`：試験水面パラメータ、静的描画のPSO指定と実際のメッシュDraw数を取得。通常Drawの既定パスを維持。`TrialWaterPass.h`、`TrialWater.PS.hlsl`、`TrialWaterProbe.h`：シーン限定の水面・診断用GPU計測。VSプロジェクトとフィルタに登録。
- `water_trial_distribution.h`、`water_trial_test.cpp`：鏡映、閉門、競合、回収水量、固定刻み、形状上限、描画あり／なしの比較。Release x64ビルド成功。`tools\tests\run_water_trial_test.cmd`、`run_farm_irrigation_balance_test.cmd`（既存1215条件）、`run_farm_water_play_test.cmd`（波紋、曲がり、休止・リセット等）成功。セーブ形式未変更。既存実セーブの再読込、任意のUndo列、Debug構成は今回未試験。

## 参考にした一次資料と判断

- [FAO-56 第8章](https://www.fao.org/4/X0490E/x0490e0e.htm)：根域の収支で流入・流出を区別する考え方を採用。FAOのET式や土壌パラメータ、単位mmをゲームの0〜1値に直接移植していない。
- [Valve, Water Flow in Portal 2](https://advances.realtimerendering.com/s2010/index.html)：ゲーム内で水面の移動方向を制御できることを重視。固定の手描き流向は掘り変わる水路に使わず、移送実績を信号源にした。
- [Mark Finch, GPU Gems 1](https://developer.nvidia.com/gpugems/gpugems/part-i-natural-effects/chapter-1-effective-water-simulation-physical-models)：波による法線変化は小さい水路でも利用できるが、大水面用の変位や別Normal Map生成は見送った。[Catlike Coding, Directional Flow](https://catlikecoding.com/unity/tutorials/flow/directional-flow/) の方向場境界の補間を次の比較候補とする。
- [Microsoft, D3D12 Timing](https://learn.microsoft.com/en-us/windows/win32/direct3d12/timing)：Direct QueueのTimestamp差と同キューの周波数から時間を求めた。CPU時計でGPU性能を推定していない。
