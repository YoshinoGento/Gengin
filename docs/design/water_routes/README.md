## 採用した方式

従来の入力は1マス1本の合成流向。対称なTでは左右成分が打ち消され、同じマス内の二経路を区別できない。今回は**境界4辺それぞれの符号付き実移送量**を使う。正は外向き、負は内向き、単位はマス容量/シミュレーション秒。1回の移送を両側に逆符号で記録し、水路と接しているだけの辺はゼロのまま。蓄えた水だけが流出する場合と、行き止まりへ流入する場合も別扱い。局所浸透、作物消費、水量の正本は変更していない。

既存の水面メッシュ上で、入口から出口まで直線または四分円の座標(u,v)を求める。uは1マスで1周期、vは進行方向左を正とする横ずれ。共有辺の中央で位置と接線が合い、両側の模様が同じ位相になる。曲率の異なる場所での物理的な速度連続性までは保証しない。分岐は実移送がある出口の経路だけを合成し、移送の比率で明暗を配分する。物理流速ではないので、少量でも模様そのものは共通の周期で進む。メッシュの外にはShaderをかけず、乾いた隣のタイルから値を補間しない。片側の入口しかない現行の移送木を勝手に多方向合流として描かない。

池は違う方向・波長・位相速度の3波を組み合わせ、長い波で短い波の位相をずらす。水深による色・透過、視線と光源を使う陰影は維持。水面用の箱の側面は捨て、密集時に箱同士が透過合成される明るい線を抑えた。落水は別の厚み付きメッシュなのでこの処理で側面を失わない。

前回の落水帯は開口幅・上流の設定水深・落差・流入量で幅と厚みを制約するため継続使用。今回は**着水量の蓄積が滴の発生閾値を超えたときに波紋も開始**する。水門が閉じても既に落ちた水の滴は寿命まで残る。角のある滴は数を増やさず、大きさ・跳ね上がり・横への広がりを変更。通常距離では分岐を伝う細い筋が主役で、滴は取水口付近の補助。飛沫だけでTeardownの粉塵のような大きな体積を表現できたとは評価しない。泡模様は経路上の模様であり、寿命をもつ泡を流量保存しながら運ぶシミュレーションではない。新たな落水発生点を任意の地形段差に一般化したわけでもない。

## 調査と不採用の理由

- [Valve：Water Flow in Portal 2](https://advances.realtimerendering.com/s2010/index.html) と [Naughty Dog：Water Technology of Uncharted、GDC 2012](https://media.gdcvault.com/gdc2012/slides/Programming%20Track/Gonzalez-Ochoa_Carlos_Water_Technology_Uncharted.pdf)：方向を持つ表面模様と泡を分ける発想は採用。制作者が事前に描いた流れは、プレイヤーが掘り直した時の移送の根拠にならない。
- [Rendering Rapids in Uncharted 4](https://www.advances.realtimerendering.com/s2016/index.html) ではオフラインの流体計算のデータと手続き的な構成要素を使う。落水の幾何・表面の陰影・着水滴を分ける点は適するが、経路の事前ベイクは適さない。
- [Catlike Coding：Directional Flow](https://catlikecoding.com/unity/tutorials/flow/directional-flow/) の格子間ブレンドは敷き詰められた水面に有用。しかし、本作の水面に無条件の近傍ブレンドを掛けると堤防や未接続の辺まで影響する。Vertex Flow Vectorの単純補間も、同じ中心頂点に2本の出口を表現できない。今回は既存メッシュ・実移送の4辺・ピクセル単位の局所座標を選んだ。自由形状・幅広の川・中心に渦が必要になれば再検討する。
- [GPU Gems：Effective Water Simulation from Physical Models](https://developer.nvidia.com/gpugems/gpugems/part-i-natural-effects/chapter-1-effective-water-simulation-physical-models)：複数の波を重ねて細部の向きを作る考え方を採用。海面変位、Normal Map生成パス、Dynamic Flow Map Texture、Compute Shaderは今回の必要条件ではない。「重要なのは流れを読めること」であって、それ用のテクスチャを持つことではない。

CPUはx64 /O2、120tickのウォームアップ後600tick、各3回の平均時間を記録した。[全CPUログ](cpu.txt)。通常の表示準備（Step/Observe/Build）の試行平均は前回2.15〜2.24、新版2.16〜2.34 µs/tick、密集では2.21〜2.29、2.19〜2.35 µs/tick。どちらも共通の辺の観測を含むので、前回リリースそのものとのCPU差ではない。頂点数は同条件で一致。実行ファイルの描画提出やUIを含む全CPU時間ではない。

## 灌漑・収穫の判断

配水ルールと本編の農具・セーブは不変更。独立した試験場の収穫比較だけ、通常の成功した収穫操作後に、控除なし条件ではその畝の水分を収穫直前の値に戻す。作物品質を後から修正する操作ではない。試験場にUndoはなく、各操作後に履歴をクリアする。PowerShellで `$env:SUIRO_WATER_TRIAL_NO_HARVEST_COST='1'` とすると無控除で試せる。既定は控除あり。

各6収穫で土壌から消えた量は1.50 U / 0 U。収穫控除が根域の過湿をリセットする役割を持つことは確認できた。それが自然な農作業であることや、楽しいことの根拠にはならない。大会で突然撤廃せず、次は**収穫後も土は湿ったまま＋受動排水**との比較を行い、頻繁な開閉を強要しないか見る。

左右対称の環状経路でも、4秒間の合流手前の移送は左0.79 U、右0。左右反転した盤面でも同じ絶対位置が選ばれた。**自由な環状路を許す本編統合前にこの偏りは直すべき**。Shaderで右側からも流れ込むように補完するのは誤表示。次の試験は、同段・同距離の合流辺だけを候補に残し、同一時点の残量・受入余裕から各辺の希望移送を求め、送り過ぎ／受け過ぎを両端で制限する。閉ループ全体の逆流・圧力計算とは区別し、保存・鏡映・更新順・既存の木状経路を通すまで採用しない。

## 実装箇所と限界

- `WaterTrialFlowView.h`：4辺データ、編集直後の古い辺の無効化、波紋の着水同期、滴形状。`FarmRenderer.{h,cpp}`：試験用PSに既存CBでパラメータを渡す。借用spanはPrepare中のみ。水面経路用の毎フレームの動的配列、新規Texture、Descriptor、UAV/Barrierは不要。新規所有GPU資源は試験用PSO。CBオフセットはコンパイル時検査。水面は不透明地形の後、Depthテストあり・書き込みなし、法線RT書き込みなし。
- `TrialRoutedWater.PS.hlsl`、`TrialWaterPass.h`、VSプロジェクト／filters：前回版を残したままShader・PSOを追加。`TrialWaterProbe.h`：アダプター名・計測状態。`WaterTrialSystem.{h,cpp}`：試験限定の収穫控除、再生操作列。`WaterTrialScene.{h,cpp}`、`tools/start_water_trial.cmd`：表示切り替えと進行。`tools/tests/profile_water_routes.ps1`：反復計測・実動画。
- `tools/tests/water_trial_test.cpp`、`water_trial_distribution.h`：2種類の掘り方、編集直後・閉門、両側の辺の符号と移送量、陸地への偽の流れがないこと、描画あり／なしの全タイル一致、有限な頂点・上限372（固定容量420）、収穫・環状路・CPU計測。Releaseと試験農場回帰成功。既存の灌漑1215条件（ほかに実刻み1/2/4倍の乾燥開始243条件）も成功。
- 固定容量・一定周期・GPUのCBレイアウトはコード定数が適切。表現値は試験Shader内で比較中のため新JSONは導入していない。本採用時に継続調整する水色・泡の強さだけを既存アート設定へ出す。別GPU・解像度・FPS視点・任意の高低差、長時間のDescriptor/VRAM推移や故障注入は未検証。既存ParticleManagerのResource確保／Map失敗時処理は今回の試験の描画経路では使わず、**配布前の別修正**。
- 通常画面の観察では、開門時のL字と後から開いた枝は以前より追いやすいが、密集した広い水面では筋が規則的な等高線にも見える。人が水門を再び開けたくなるかは未検証。提出判断には、HUDを隠して初見の人が開門・新しい分岐・閉門を指せるか確認する。その結果と密集時GPU予算で、本編への接続可否を決める。
