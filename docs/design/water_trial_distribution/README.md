# 満水の分岐で、なぜ土が乾くのか

2026-11-27。対象は本編セーブを使わない Water Trial。**三作目の47点を「分岐の戦略性」として採用しない。** 水源から末端への移送は足りている。問題は、供給経路から決まる浸透速度と、収穫時の水分減少の組み合わせ。本編の収穫・灌漑規則は変更していない。

## 条件と測定

- 実装の既定値の5×4、ニンジン2畝、初期土壌水分0.25、降雨・手動散水なし。工事と播種を終えてから計時。固定1/60秒で灌漑→生育→成熟株を同じtick末に収穫・三作目までは即再播種。試験終了後に本編データを読むことも書くこともない。
- Uは1水路マスの容量を1とするゲーム内単位。土壌水分1.00は100%。以下はシミュレーション時間で、操作時間・実時間のフレーム性能ではない。
- [CPUの生出力](cpu-trace.txt)には1・10・20・30秒時点の**各辺の累積移送量**、両畝の実流入・実消費、各収穫の直前直後を収録。辺は親>子、マス番号は5列の行優先。辺の移送は内部移動なので全体収支には加えない。

### どこで差が生まれるか

1. 池からの補給上限は0.50 U/s、各親が送れる上限は0.40 U/s。すべての辺は同一時点の親在庫・子の空き容量を読む。受け取った水を同じtickで次の辺に送り直さない。開いた池岸は1か所。BFSで非上りの各水路に最初の親を一つ割り当てる。
2. 分岐の親は予算を子の数で等分する。最初の1秒で14→13は0.400 U、13→12は0.393 U、12→7と12→17は各0.193 U。満水の子の余った取り分は兄弟に再配分されない。今回は両末端が満水なので、これが品質低下の原因ではない。
3. 浸透にも経路係数が掛かる。耕作済み・取水許可・隣が同じ高さ以上の水のある水路であることが条件。流量ではなく最強の候補一つを選ぶ。土壌水分0.70まで定率、以後減速し0.96で停止。同じ給水元に複数の畝が要求し在庫不足なら比例配分する。分岐末端は両方とも0.05×0.9³÷2、一本道は手前0.05×0.9⁵、奥0.05×0.9³。**水路が満水になってもこの差が残る。** これは水の質量損失ではない。
4. 分岐では実消費1/55 U/sを引いた回復余力が約0.000043 U/sしかない。初収穫の水分0.250214から既存の収穫コスト0.25を引いて0.000214。30秒時点でも0.000683。三作目の約36.02秒は両畝ともすべて乾燥区分。一本道の三作目は手前が低水分19.28秒／適正0.28秒、奥は低水分2.00秒／適正13.08秒。品質は収穫直前の水分だけでなく生育中の平均効率・成熟度・地形・養分等を使うので、47点自体を水だけの公式とはしない。
5. **反証用の単独介入**：分岐で水源補給だけ2倍→47/47、辺移送上限だけ2倍→47/47、土への回復率だけ2倍→70/70。テスト中だけ既存ルール引数を変更した。2倍が適切な製品値だと示すものではない。三作の最大1更新収支誤差は5.97×10⁻⁸ U未満。

### 公平性・遮断

- 各形状で6,000固定更新（100秒）。通常の東岸、東岸で掘削順を逆転、同位置の独立水源、独立水源ごと左右反転し掘削順も逆転、を対応マスで毎tick比較。全マス水量・水分・生育・辺の累積移送・各畝の収穫tick・品質が一致。独立水源は左右反転用の治具で、西岸からの取水を本編に追加したわけではない。工事中に水を流しながら掘るケースは同条件ではない。
- **ループには別の偏りがある。** 対称な二経路が中央12に合流する盤面で、実際の親は左11だけ。鏡映なら13となるが、再構築すると左が先。等量の残水が左右にある単独畝でも、1tickの土への供給は左0.00075／右0 Uだった。鏡映で今回の品質差が消えることも、任意の盤面で偏りがないことも示していない。
- **閉門逆転は修正候補。** 10秒給水した分岐の門を閉じると、新規流入は0のまま、残水から畝への速度が0.018225→0.045000 U/sへ上昇。未接続になると供給強度が経路係数0.3645から一律0.90に切り替わるため。残った水が使えること自体は正しい。「閉めるとよく染みる」ことをテクニックとして売らない。
- 次の比較案：辺の搬送は今の有限量のまま、浸透上限を**その場の水深・畝との高さ・土壌水分**から決め、同一給水元への要求総量は在庫で制限する。接続中と遮断後で同じ式を使う。まず木構造だけで検証。ループはその後、親一択と「複数辺で水位差に基づく同期移送」を別実験にし、今回の改善と混同しない。初めから浅水方程式を導入する理由はない。

## 画面と使い方

- リポジトリ直下で `tools\start_water_trial.cmd inspect`：両畝・分岐・開始10秒・一時停止。左上の **I Soil** をクリック、または I で診断を切り替える。「Low, holding」は低水分かつ直前の変化が実時間ではなくゲーム内1分当たり1ポイント以内。Ditchは**実際に送った水路の更新後在庫**、Inは実流入、Useは生育更新前後の実減少（両方とも水分の百分率ポイント/秒）。0と丸めて表示する値は厳密な0ではない。給水元なしは在庫0と区別する。
- 引数なしは空の試験農場。F6で両畝に変更・リセット、1溝／2耕す／3種／4じょうろ／5収穫。クリック、または矢印＋Space。Pで再開／停止。手前2・奥16を耕し播種、池岸14を開き13・12・7・17を掘ると分岐。一本道は14・13・12・11・6・1。門を再操作すると閉じる。作業時の診断は次の固定更新まで無効。Undo・時間倍率は試験農場に導入していない。
- `tools\start_water_trial.cmd compare C`：開門0.8秒を固定。F1/A＝水面・流向、F2/B＝落水帯、F3/C＝CPU飛沫付き（キーはF1～F3、クリックでも可）。[診断なし](inspection-off.jpg)・[診断あり](inspection-on.jpg)は同じ10秒。[旧C](../water_trial_20261127/C.jpg)・[現B](sheet-48.jpg)・[現C](spray-48.jpg)は同じ48更新、Releaseの通常カメラ。拡大合成やイメージ図ではない。
- Cでは同じ10スロット・同じ発生量・寿命0.31秒を保持。落水帯の足元から、マス幅に比例した半径と横広がり、放物線、上昇／下降時の縦長形状、各面の幾何法線による簡易明暗を使った。CPU側の表現で、水が増えることはない。煙の体積レンダリングを再現したものではない。比較静止画でも差は局所的。見栄えの優位、動きの好ましさ、透明画素の性能は未検証。

## 調査と判断

- [Mechanistryの公式開発記録](https://store.steampowered.com/news/posts/?appids=1062090&enddate=1705410130&feed=steam_community_announcements)では、水域があっても状態に応じて灌漑範囲が変わる。今回も「水が見える」と「畑が回復する」を分ける発想には賛成。ただし土の色だけでは、未到達と、流入・消費が釣り合う場合を区別できない。
- [Kleiの公式更新告知](https://steamcommunity.com/app/457140/announcements/)の配管用 Pipe Flow 表示と同じく、在庫と流れを分け、必要時だけ調べる方針。20マスに常時矢印・全辺流量・警告を重ねる案には反対。まず二畝だけの診断で原因を説明できるかを試す。
- [Dennis Gustafssonの講演概要](https://graphicsprogrammingconference.com/archive/2025/)はボクセル空間とライティングの組み合わせの参考。煙用の方式を小さな農業用水路に移植できるという根拠ではない。次の見せ場は大規模粒子化ではなく、**実移送量に連動する落水帯の幅と着水の広がりを一緒に変える**こと。水面模様を速くすれば実流速を再現したことにはならない。移送量を断面積で割る等の仮定が必要。今回の水面模様の位相速度は従来どおりで、辺の実移送で有無と強度のみ変わる。

## 品質レビュー・検証範囲

- 所有権：水・土の正本はFarmGrid、配水はFarmIrrigationSystem。試験Systemは実移送と生育前後を1更新に限って2件の固定長の観測値にする。Renderer・UIは読取のみ。診断値は時系列積分せず保存もしない。残水でも実際に送った辺／給水元だけを観測。無効マス・未測定・非作付け・最新編集を区別。整数型が負になり得た作業enumに固定の符号なし基底型を指定し、Count以上の入力を配列参照前に拒否。無効値の試験あり。
- 固定更新中、観測spanは灌漑更新をまたがない。生育更新は灌漑側バッファを再確保しない。固定長の頂点は最大366（20水路×6＋21帯×6＋10滴×12）、シナリオ試験で有限値・頂点上限・閉門後の消滅を検査。20枚の帯は試験の固定1/60秒前提であり、高周波化する際は滞空時間をカバーする数を再評価。農具Undo履歴は試験専用に破棄し、Undo対応を装わない。
- GPU：飛沫は既存の透明VB/CBと同一DrawInstancedに合流。追加の水用Descriptor、UAV、Barrier、独立Drawなし。深度テストあり、深度書込みなし。CPUが同一Upload領域を再利用できるのは、現行DirectXCommon::PostDrawのFence待ちが前提。複数フレーム並列にするなら領域をFenceで退役させる必要がある。[Microsoft公式解説](https://learn.microsoft.com/en-us/windows/win32/direct3d12/fence-based-resource-management)
- UIの診断は無料ではない。固定長6行だが既存SpriteTextは文字単位のSprite・描画であり、初回表示で確保する。観測の丸め値が変わった場合のみ文字列／レイアウトを更新し、閉じれば診断文字は描かない。通常HUDの既存formatとグリッド測定の複数回走査は残る。Particleの頂点は固定長、効果用Uploadへのコピーは1回。VRAM総量・実Draw数・GPU時間・Overdraw・他GPU/DPIは未計測。面積の増えた飛沫を「負荷不変」とは言わない。
- 配布前の未解決事項：ParticleManager.cppのinstancing/material/VB生成で戻り値とMap失敗を扱わず、GPU用リソースにも生成直後の参照箇所がある。欠損時は描画以前の初期化で落ち得る。試験飛沫から使用しないためエンジン全体は変更しなかったが、配布前には生成・Map・Descriptor取得失敗の注入、部分初期化の解放、失敗状態でのUpdate/Draw抑止を別修正で確認する。CanalLabの部分掘削も今回の経路外。両方とも修正済みではない。
- Windows x64 Releaseビルド成功。CPU /O2・/W4・/WXの `tools\tests\run_water_trial_test.cmd` 成功。既存 `run_farm_irrigation_balance_test.cmd` は1,215ケース（実1/2/4倍ステップの乾燥開始243件を含む）成功。`run_farm_field_controls_test.cmd` 成功。倍率の結果は既存灌漑の検証であり、新しい表示の倍率実機試験ではない。実画面で確認したのは通常カメラでの診断オン／オフとC→Bのクリック切替。Debug、PIX、故障注入、長期プレイ、面白さの比較は未実施。

## 次に進む条件

1. 試験モードのみで局所浸透案と現行を同じ盤面で切替比較。門を閉めた1tick後、在庫が減ったのに畝の給水速度が急上昇しないこと。水収支、即時の流入停止、残水の継続、左右反転の木構造、単線・分岐の三作成績を再測定。スコアを同点にすることを目標にしない。
2. 初見プレイヤーに10秒の分岐を見せ「どこに水が残っているか」「なぜ土は乾いたままか」を通常画面→診断ありの順に聞く。答え・判断までの秒数・余計に掘った回数を記録。常駐HUDが必要という結論はまだ出さない。
3. B/Cの順を入れ替え、通常距離・開門と閉門の動画で「どこに落ち、いつ止まったか」を聞く。変化を識別できなければ粒子数より先に着水面と帯のシルエットを試す。GPU化は表現が有用でCPU・描画に実測ボトルネックがある場合だけ再審査。
