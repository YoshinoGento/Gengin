# 本編移行判定：環状路・土壌排水・水面描画

2026-11-27。試験場での採用候補は「水源からの距離を利用した複数辺移送」「現行の曲線Pixel Shader」。本編の配水既定値、セーブ形式、大会、作物表は変更していない。以下の品質はニンジンのゲーム内評価値で、遊びやすさの人間評価ではない。

## 配水

旧方式は幅優先探索の最初の親にだけ水を送る。対称な菱形でも中央への左右の移送は4秒積算で0.79 / 0 U。左右反転しても配列上の同じ側を選ぶ。これは戦略性ではない。

比較した第1案は水位差による四近傍移送。全辺の流出要求を凍結した在庫から算出し、送出・受入を制限した。対称性は改善したが4秒で0.01163 / 0.01163 U。長い一本道・控除ありの3作目が手前46.68→99.08秒、奥49.75→82.57秒になった。水位差そのものが悪いのではない。差が消えるほど移送も弱くなるこのモデルは、既存の水路にそのまま代入できない。結果は [試行ログ](head-experiment.txt)。不採用の計算はゲームに残さない。

採用候補 `CanalTransport::LocalEdges` は物理流速を解かない有向配水ネットワーク。従来の到達判定を使い、水源からの最短距離が一つ増え、上り坂でない辺をすべて対象にする。単位Uは1マスの容量。供給後の在庫と毎秒の移送能力の小さい方を出辺に等分し、受け手の空き容量が不足すれば全ての流入を同比率で制限する。入ってきた水を同じtickで再送しない。各辺の符号付き実移送を両端に記録し、描画は親IDから再構成しない。別の水量バッファを永続化しない。

- 菱形4秒：左右 **0.50 / 0.50 U**（60 Hzの1倍、1ステップ4倍の両方）。最大1ステップ収支誤差 **2.98e-8 U**。複数水源・非対称初期在庫・高低差を含む盤面を180度反転して辺ごとの計算を比較。流出能力・在庫・受入容量・非負性、閉鎖、実際の掘削Undo/Redo、描画非干渉を回帰試験。
- 分岐だけ・一本道だけの配置では旧計算の品質と収穫時刻を維持。同じ距離の辺に横流れを作る方式ではない。閉門後は外部供給が止まり、孤立した水は隣の土へ浸透する。畝のない孤立した環の水位は均されない。閉鎖後の振幅増大なしと、水位の平準化・自然な渦の再現は別。
- `GetUpstreamTileIndex` 等は従来の到達予測用。本編の誘導・予測・到達前線に対して真の移送を示すAPIではない。これを直さずに表示だけ移植しない。

**原因の切り分け。** 別の3起動×64サンプルで、現在の経路Shaderから流線部分だけをコンパイル時に除いた対照を追加した（`control-edges-*.csv`）。密集720pは旧材質28.30、流線なし23.98、流線あり35.94 µs。1080pは順に44.70、36.90、57.22 µs。対照と現行のDraw・頂点・PS実行数は一致し、流線の計算とそれに依存する合成を消すと中央値がそれぞれ11.96、20.32 µs小さくなる。個別のatan2やループが何µsかは未分離。前回の「2.9倍」を固定倍率にせず、現在の規模ではこの可視化に費用を使う。対照には流向が見えないので採用しない。

PIX 2509.25で実際の密集1080pフレームを取得。[イベントとカウンター](pix-counters.csv)、[通常カメラ](pix.png)。Query区間の87 Drawを合計するとIA=3,540、PS=480,821でゲーム内統計と一致。Global ID 268と269は各36頂点で179,029／103,597 PS実行、合わせて58.8%。多くの小さな分岐だけがコストを支配するという仮説は支持されない。PIXでID 265→352のRTV0を書き出すとRGBが変化した画素469,370。PS実行／変化画素は1.024。これはdiscard、同色出力、helper等を区別せず、幾何学的なOverdraw率そのものではない。このフレームに大規模な全面重ね塗りを示す結果はない。PIXの個別Drawの時間を足してパスの時間にしない。PIX再生のDebug Layerコマンドは成功、全シーン・複数GPU・デバイス喪失の認証ではない。Nsight GraphicsはこのPCのインストールに見つからず、命令単位のstallは未測定。

CPUは実際に時間を進めた別テスト。120tickのウォームアップ後600tickを3回。新移送・15水路で試験Systemは4.87～5.18 µs/tick、CPU表示データ生成3.31～3.73 µs/tick。描画コマンド提出・Presentは含まない。5×4は本編初期演出相当であって任意の保存盤面の上限ではない。全面水路・1水源・初期半量の合成ストレス（30tickウォームアップ＋120tick、3回、配水CPUのみ）：32×32は0.175～0.176 ms、保存形式上限の128×128は3.20～3.26 ms。大盤面を製品仕様にするなら、地形構築・状態書戻し・計測用走査の内訳を先に測る。128×128でのGPU時間・本編総フレーム時間は未測定。

### 採否

- 曲線UVを全頂点に焼く案は保留。四角・少頂点の水面の線形補間では角の円弧が崩れ、複数方向の合流を一組のUVでは表せない。曲線用に頂点を増やす価格に見合う問題は初期規模で確認できなかった。Vertex Shaderへの全面移動も同じ理由。これらとFlow Map Textureは実装・実測していない。
- 地形の接続候補と毎tickの移送量を区別する。地形変更時の接続キャッシュには余地があるが、乾湿や流量までキャッシュすれば閉門・Undo直後に誤表示になる。現在の経路リストはSystemが所有し容量を再利用するが、トポロジー走査は各固定更新で行う。新Texture、Compute、GPU Particle、専用Descriptorは増やさない。
- 旧・新ともCPU飛沫の上限10個・1滴4面。落水の幅・厚みは実流入と開口・落差に結びつけたまま、下端の輪郭を少し変動させ、水滴を放物線の接線に向ける。上昇と落下で向きが変わり、頂点数は増えない。[調整前](splash-before.png)／[調整後](splash-after.png)／[14秒の左右比較](compare.mp4)。同一停止フレームの取水口周辺で変化したのは248画素。開門・分岐・閉門は同じtickで実行、動画は開門のフレームで揃えた実時間録画（同期誤差あり）。開門前線の計算速度は盛らない。水膜から飛びちぎれる独立粒子や任意の段差の落水を実装したわけではない。通常カメラでは流線と水膜の方が分かりやすく、粒子の迫力や操作の楽しさは人間による未検証。密集場では水面に四角い色境界も残る。

## 安全性と移行手順

- Systemが在庫・辺の実移送を確定。FlowViewが値を固定配列にコピーし、UI・Rendererは書き戻さない。負添字・マス端の折り返しを避け、株と地形変更後のサンプルを無効化する。GPUのQueryHeapとReadbackは試験所有。既存のDirect QueueでResolveしFence完了後だけMap／slot再利用。ReadbackはCOPY_DEST固定、追加のBarrier・Descriptorは不要。既存の毎フレーム完了待ちを前提にし、frames-in-flightを導入するならslotと破棄をFence単位に変える。1080pは既存ターゲットの画素容量が2.25倍となるが、VRAM実使用の上限値は未計測。
- ParticleManager初期化：入力・8個のDescriptor空き・UAV確保・Upload Mapを使用前に確認し、WinMainが捕捉する初期化例外で停止する。9つのMapで共通の検査を使い、失敗時のポインタを公開しない。割当失敗、MapのHRESULT失敗、成功なのにnull、成功の4経路をスタブで検証。起動中断・プロセス終了を前提とし、再試行・ホットリロード用のロールバックではない。実デバイスでVRAM枯渇を発生させた試験ではない。
- 本編への一括移行は不可。① 診断・到達予測が使う親IDを「到達」と「実移送」に分離。② 同じセーブの複製で3作物・雨・閉門・Undo/Redo・再ロード・大会30日を比較し、先に辺移送だけを任意切替で導入。③ 描画は別スイッチで有効化し、密集時の継ぎ目、FPS/見下ろし双方、池以外の開口・段差を確認。④ 排水は最後。過湿への対処が無意味になる、別GPUでフレーム予算を超える、畑が先に濡れて見える場合は当該機能だけを保留。初見プレイヤーが診断なしで分岐先と閉門後の残水を指せるかで採用判断する。

## 起動・再現

Release x64をビルドし、ルートから `tools\start_water_trial.cmd compare C`。F8で開門・分岐追加・閉門のリプレイ。環境変数 `SUIRO_WATER_TRIAL_TREE=1` は親方式、`SUIRO_WATER_TRIAL_DRAIN=1` は控除なし＋受動排水、`SUIRO_WATER_TRIAL_NO_HARVEST_COST=1` は控除なし（排水優先）。指定しなければ新しい辺移送・収穫控除あり。通常のゲームはこれらの配水設定を読まない。

- `tools\tests\run_water_trial_test.cmd`、`run_farm_irrigation_balance_test.cmd`、`run_particle_upload_test.cmd`。試験場CPU、既存灌漑1,215配置条件・乾燥開始243条件、Map異常系が成功。
- PowerShell：`./tools/tests/profile_water_routes.ps1 -Integration -LocalEdges -Dense -FullHD`。5水路はDenseを省略、720pはFullHDを省略。診断比較はAblation、飛沫の実画面はSplashComparison、動画はさらにVideo。CSVは各プロセスのPIDで区別する。
- 主要実装：FarmIrrigationSystem（辺・上限・収支）、WaterTrialSystem（土壌条件）、WaterTrialFlowView（実移送・水滴）、WaterTrialScene／TrialWaterPass／TrialWaterProbe（選択・描画・測定）、TrialRoutedWaterと診断用Shader、DirectXCommon（内部解像度・UAV失敗）、ParticleManager／ParticleUploadMapping。測定用スクリプト、回帰テストとVSプロジェクト登録も更新。

## 一次資料と適用範囲

- [Meiほか：Hydraulic Erosion](https://doi.org/10.1109/PG.2007.15)。各方向の流出を利用可能量内に制限する考えを参照。侵食や仮想パイプの速度積分は導入していない。
- [FAO 56・第8章](https://www.fao.org/4/X0490E/x0490e0e.htm)。根域収支で消費と深部浸透を別に扱う考えを借用。試験の係数は現実の土壌推定値ではない。
- [Microsoft・HLSL最適化](https://learn.microsoft.com/en-us/windows/win32/direct3dhlsl/dx-graphics-hlsl-optimize)、[PIXハードウェアカウンター](https://learn.microsoft.com/en-us/windows/pix/gpu-captures/hardware-counters)、[NVIDIA Shader Profiler](https://docs.nvidia.com/nsight-graphics/UserGuide/shader-profiler.html)。PSから低頻度処理を移す一般論と、このメッシュで補間できるか・実際に速いかを区別。
- [GPU Gems・Effective Water Simulation](https://developer.nvidia.com/gpugems/gpugems/part-i-natural-effects/chapter-1-effective-water-simulation-physical-models)、[Chentanez & Müller・原論文](https://matthias-research.github.io/pages/publications/hfFluid.pdf)。水面と小スケールの表現を分ける利点はあるが、大水域用の双方向粒子ソルバーを5×4の農場で再現する根拠はない。
