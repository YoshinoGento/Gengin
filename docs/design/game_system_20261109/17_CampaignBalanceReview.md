# 30日間の収支・拡張・水源配置の検証 / 2026-11-11

## 結論と今回の範囲

通常Releaseの基本操作と、本番Systemを使った18ケースの30日シミュレーションを確認した。
**拡張が序盤で終わり、所持金が余る経路が見つかったため、ゲーム全体のバランスは未完了。**

今回は検証コードと記録を追加した。直前に調整した給水速度0.050/秒を維持し、水源の設置費・個数上限・拡張条件・売却価格・採点式は変更していない。新しいDebug画面、セーブ形式変更、提出ZIP更新はない。

## 比較方法

`tools/tests/farm_campaign_balance_test.cpp`が、本番のSimulationStep・ToolAction・Economy・Development・Contest各Systemを呼ぶ。日付、成長度、品質、所持金を直接書き換える合成データではなく、初期資金300G・種0個から購入、準備、栽培、収穫、売却、出品へ進める。

| 比較軸 | 条件 |
|---|---|
| 土の管理 | 毎作堆肥を使う / 堆肥を使わない |
| 配置と拡張 | 1水源で拡張 / 2水源で拡張 / 1水源で拡張しない |
| 時間速度 | 1倍 / 2倍 / 4倍 |
| 合計 | 2 × 3 × 3 = 18ケース |

- 初期農地5×4。中央列に水源と水路を配置する。2水源版は中央列の4行目を水路から水源へ置き換え、占有マス数を同じにする。
- 初期栽培は2区画。拡張できるたびに新しい行へ2区画追加し、最大6区画を栽培する。拡張なしは2区画のまま。
- 1～10日はニンジン、11～20日はトマト、21～30日はかぼちゃ。高さは段階の解放範囲内に収める。
- 各段階で3回栽培する。最初に栽培・売却し、次に害虫予兆日6・16・26日目をまたぐ栽培、最後に雨の日8・18・28日目の栽培を行う。
- 雨の日の収穫物1個を保護・予約し、10・20・30日目に出品する。残りは売却し、条件を満たせば拡張する。
- 水やりで適正水分帯の中央まで準備した後、水路で給水する。5シミュレーション秒ごとに全区画を調べ、適正帯の下側25%で取水ON、上側25%でOFF。害虫は同じ確認時に駆除する。

**人の操作時間は再現していない。** 複数区画を同時に確認し、準備・購入・収穫を待ち時間なしで実行する。4倍速では確認間隔が実時間1.25秒になる。操作負担、初心者の成功率、一般的なプレイ時間の測定ではない。
また、雨・害虫の日に合わせた待機があるため、このテストの待ち時間を通常プレイの退屈さの指標にはしない。

審査点は品質点と大きさ点の合計。合格ラインは10日目65点、20日目75点、30日目85点。
最終資金は30日目の出品後の所持金。拡張日は、実際に拡張操作を行った日であり、理論上の最速日ではない。

- 全18ケースで30日目まで到達し、3回の出品、3回の害虫予兆と駆除、3回の雨を通過した。
- 堆肥ありは全段階で合格、堆肥なしは全段階で不合格。水分だけでなく養分管理にも審査上の意味がある。
- 1/2/4倍速で収穫数・拡張日は一致。最終資金差30G以内、段階得点差2点以内の回帰条件を通過した。完全なビット一致ではない。
- 堆肥あり・1水源・拡張ありでは、種代4,860G、売上19,775G。`300 - 4,860 + 19,775 = 15,215G`が本番の所持金と一致した。
- 同条件の取水変更は150回、準備の手動水やりは116回。開始時・収穫後の取水操作も含む。操作負担が少ないとは判断できない。

## バランス上の問題と判断

### 1. 拡張が初回審査より前に終わる

現行の拡張条件は累計売上500G / 1,500Gで、拡張費は無料。上の手順では6日目に最大30マスへ到達する。
「中盤・終盤にも農場が発展する」狙いに対して、売上だけの条件では早すぎる経路がある。実装が動くことと、成長システムの進行が適切なことは別。

次は、売上だけを引き上げる案と、品評会の段階に拡張を結び付ける案を比較する。**現時点では未採用**。旧セーブの拡張済み農地を縮めたり、未入賞で永久に発展不能にしたりしない方針が必要。

### 2. お金を貯める意味が弱い

現行では水源、水路、造成、堆肥、土地拡張が無料で、今回の手順で支払ったのは種代のみ。
拡張なしでも4,809G、拡張ありでは15,215G残る。「資金不足が起きない」という確認にはなるが、経営上の選択がある証拠にはならない。

まず土地拡張や任意の設備投資に資金を使う案を検討する。基本の復旧操作をいきなり有料化すると、再開支援で種を受け取っても育てられない状況を作るため、救済との整合が必要。

### 3. 水源を増やせば常に有利、ではない

この同一占有マスの比較では、1水源と2水源の審査点・拡張日・取水変更回数は同じ。最終資金差は6Gに留まった。
既存Irrigationの接続は上流を1つ選ぶBFSであり、流量が単純加算される仕組みではない。

したがって、この結果だけを理由に水源へ費用や上限を追加しない。別系統・短縮経路・畑の占有数が異なる配置は、[給水バランスの比較](16_IrrigationBalance.md)と分けて評価する。全配置で水源追加が無意味とも、無料・無制限で適切とも断定しない。

## 通常Releaseで確認したこと

元セーブを使わない別コピーで、以下を通常のマウス操作から確認した。

1. タイトルから農場選択、開始演出、新規大会農場へ進む。
2. 地形メニューで水源と水路の設置をプレビュー・確定し、隣接する畑を耕す。
3. HUDの取水操作でON → OFF → ONにする。OFF時に水分44%を維持し、再開後は53%、100%へ上昇した。
4. 種屋でニンジンを購入する。300G → 240G、種0 → 1。畑へ戻って種まきし、種1 → 0。
5. 過湿時の案内と、取水停止後の案内変更を確認する。以降、水分が100% → 97% → 74%と減る間に作物が成長した。
6. 検証用ウィンドウを閉じ、対象のウィンドウが残っていないことを確認する。

CDBでこの経路にAccess Violation / heap破損の停止はなかった。C++ first-chance例外ログはあり、すべての例外がないという意味ではない。デバッガー起動ラッパーの終了コードは0。**以前のメモリ破損の原因は未特定で、修正済みとはしない。**
土地拡張そのものの実画面操作や、30日を人が遊ぶ確認は今回の範囲に含めない。

## 再実行・安全性・未検証

```powershell
tools\tests\run_farm_campaign_balance_test.cmd
```

実行結果: `generated/campaign_balance_results.log`、ケース進行: `generated/campaign_balance_status.log`。
通常操作のデバッガーログ: `generated/layout_balance_native_cdb.log`。
テストはC++20・`/O2 /W4 /WX`でコンパイルして実行した。今回の追加は検証コードと文書のみで、ゲーム本体のDebug / Release再ビルドは行っていない。実機確認は直前の給水調整を含むRelease全再ビルドの実行版を使用した。

- テストのCampaignがGridと各Systemを所有する。StageAccessの参照先は同じインスタンス内にあり、コピーを禁止する。選択、収穫記録、拡張添字を検査し、1ケース最大120,000フレームで制限する。
- 毎フレームのGridコピーや新しい本番の動的確保は追加しない。Toolの履歴は区切りで消去する。拡張時の既存Snapshot再配置では、古いTileポインタを保持しない。

- 取水を開きっぱなしにする失敗経路は既存の給水・季節テストが担当する。今回の成功前提の日程に同じ失敗経路を混ぜると栽培が予定日に間に合わないため、別の検証として分ける。
