# 天候・災害 : 水の配り方を変える理由

状態: **予報付きの雨は初回実装・自動検証・Debug/Releaseビルド済み（2026-11-10）。比較画面と通常農場の実操作は未確認。** 採用したルールとDebug手順は[雨システムの実装記録](08_RainSystem.md)。以下は初期提案であり、台風・乾燥期・水路詰まりまで採用・実装したわけではない。

## 先に作る価値があるもの

| 候補 | 起こる変化 | プレイヤーの判断 | 実装上の不足 |
|---|---|---|---|
| 雨 | 土壌水分が増え、給水し続けると過多になりやすい | 畑への取水を止める、雨の前に水量を控える | 雨量と土壌への入力、予報、保存 |
| 乾燥期 | 水源の補給が減り、土壌水分が減りやすい | 重要な畑を優先、貯水を活用、栽培数を調整 | 補給・蒸発への天候係数、残水量の理解 |
| 台風 | 大雨や強風で農場条件が変化 | 予報から収穫や給水方針を変える | 雨の土台に加え、被害と復旧の仕様が必要 |
| 水路の詰まり | 一部の下流へ水が届きにくい | 詰まりを発見・除去、経路の見直し | 障害状態、接続/流量計算への反映、除去操作 |

水路詰まりも今回の新しい提案。台風・雨・乾燥・詰まりを同時に入れる前提にはしない。

最初の天候としては**予報付きの雨**を推奨する。現在の畑ごとの取水ON/OFFが対策として使え、水管理というゲームの中心とつながる。ただし雨だけで避けられない水分過多になる設定では、取水を止める選択が意味を失う。

## 体験の流れ

```text
翌日は雨の予報
  → 水分が高いトマト畑を確認
  → 取水を止める / 現在の給水を続ける
  → 雨と給水に応じて土壌水分が変化
  → 生育履歴と品質に違いが出る
  → 結果を見て次の雨への対策を変える
```

雨は被害だけでなく、給水の手間が減る利点も持たせる。乾燥期も「突然水が消える」ではなく、予報と補給量の変化を見せる。

## 現状と混同しないこと

- タイトルの風・雲・昼夜は見た目の演出。農場の天候シミュレーションではない。
- 現在の水路の貯水と土壌水分は別の値。水路が満ちているだけで土の洪水を実装したことにはならない。
- 取水ON/OFFは畑への給水を止める機能であり、地表の排水や水源の流量調整ではない。
- 水源は補給される。乾燥期を作るなら補給と消費の収支まで変える必要がある。
- 水分過多は既存の成長/評価へ反映されるが、枯死や地形破壊があるわけではない。

## 台風・洪水は後に分ける

台風で地形を壊す案は、経路再構築・Undo・作物占有・復旧費・保存・ゲーム継続可能性まで影響する。演出だけ先に豪華にしても、課題のゲームシステムを満たす根拠にはならない。

地表の洪水を採用する場合は、土壌水分とは別の地表水量、移動先、流出先、容量上限を設計する。青い面を出すだけの表現と、水収支を持つシステムを区別する。完全な流体物理は必須ではない。

最初の版では、台風による全作物消滅・水源破壊・不可逆な進行不能を採用しない。

## 責務・ルール・検証

`FarmWeatherSystem`（仮称）は予報と天候状態を管理する。水量の変更はIrrigation/Soil側が受け取り、成長と品質は既存の履歴計算へつなぐ。描画Systemは天候を読むだけで農地状態を変更しない。

予報は確定した予定から表示し、毎回画面を開くたびに変えない。予報中の保存復帰でも同じ天候になるよう予定・乱数状態・版を保存する。天候係数は版付き設定にまとめ、初期は`constexpr`のルール表、調整頻度が上がったら検証付きJSON化を検討する。

- [ ] 同じ初期状態で対策の有無を比較し、雨量・給水量・土壌水分の違いを確認する。
- [ ] 水量が負にならない、上限超過を定義どおり処理する、NaNを伝播しない。
- [ ] 予報→発生→終了を倍速・保存復帰・複数日跨ぎでも一致させる。
- [ ] メニュー中に時間が進まない。時間送りは予報の対応期限前に止まる。
- [ ] 同じ負のイベントが連続し続けない制約を設け、悪条件でも回復経路を残す。
- [ ] 雨粒や雲による画面の見えにくさ、DrawCall・CPU/GPU負荷を計測する。
