# 着手順と完成チェック

確認日: 2026-11-09。**この文書は未着手タスク**。調査でコードが見つかっただけの機能を、新たに完成した機能として扱わない。

## 今回見せるゲームシステムの第一候補

**害虫を発見し、対処するかを選び、収穫品質と大会結果の違いを確認する。**

虫を飛ばすだけでは不足。普通のRelease操作で「発生→判断→対策→結果」が一通り遊べることを完成の単位にする。

学校画像の11/11までを想定すると、11/9時点から害虫・台風・ランク・拡張を全部完成させる前提は危険。以下の順に完了を確認し、期限に間に合わない項目を実装済みとして提出しない。最初の実装規模と残り時間を確認して、提出範囲を決める。

## A. 仕様確定

- [ ] 最初の追加は害虫に絞る。予兆、対処猶予、品質への影響、発生上限を決める。
- [ ] 初回版では拡散・虫除け植物を外すか決める。外した場合は未実装として残す。
- [ ] 新規大会だけを対象にするか決める。既存農場・フリーに無断で被害を加えない。
- [ ] 品質評価の版と大会への影響を決める。既存の65/75/85点を理由なく変更しない。

## B. 状態とSystem

- [ ] 害虫状態・育成被害履歴・処理済み日付・乱数状態を設計する。
- [ ] 予兆、駆除、日末被害、収穫時の記録確定をSystemへ実装する。
- [ ] 現行の日付更新・大会停止の順序に統合する。
- [ ] メニュー、Preview、Undo/Redo、タイムライン復帰時の扱いを統一する。
- [ ] 保存版の移行を実装し、不正データでは現在の農場を変更しない。
- [ ] 通常更新と時間送りに共通の更新経路を用意し、新イベントを片方だけに実装しない。

## C. 通常プレイへ接続

- [ ] 畑に予兆と発生状態を見せる。対象を選択でき、必要時だけ短い説明を出す。
- [ ] 虫取り網の入力を専用Systemへ渡す。UIに被害計算を書かない。
- [ ] 対策成功を表示し、表示を閉じても駆除が二重に起きないようにする。
- [ ] 収穫と結果画面で、品質への影響を具体的な履歴から説明する。
- [ ] Debug専用の操作なしで体験できるRelease導線を作る。

## D. 検証

- [ ] 固定seed・同条件で対策あり/なしを比較する。イベントを再現可能にする。
- [ ] 1/2/4倍速で日末処理が一度ずつ起きる。予兆を見逃す前に必要な停止を行う。
- [ ] 予兆中/発生中/駆除後/収穫後の保存復帰を確認する。
- [ ] メニュー・Preview中の停止と、取消・Undo後の整合を確認する。
- [ ] 古いセーブ・確定済み大会・予約/保護した収穫記録を壊さない。
- [ ] 種なし、作物なし、全畑成熟、日10/20/30、日30超過でも進行不能にしない。
- [ ] 既存の育成・品質・サイズ・大会・保存・売買・段階解放のテストを再実行する。
- [ ] Debug/Releaseをビルドし、独立コピーで入力・表示・終了を確認する。
- [ ] 初めて遊ぶ人に説明なしで操作してもらい、気付けるか、対応できるかを記録する。

## E. 技術レビューの必須項目

| 観点 | 確認する内容 |
|---|---|
| nullptr・寿命 | Sessionの破棄/ロード/再初期化後に古いGridやUI対象を参照しない |
| OOB・初期化 | 対象TileID、隣接座標、セーブ由来の状態・日付・数値を検証する |
| 所有権・責務 | 永続状態とSystemの所有者を明確にし、UIやSceneへロジックを追加しない |
| コピー・確保 | 毎フレームのGridコピーや一匹ごとの動的確保を避け、必要範囲だけ更新する |
| ルール値 | マジックナンバーを分散させず版付き`constexpr`表に集約。JSON化は入力検証込みで検討 |
| CPU/GPU | 日境界更新のスパイク、虫表示のDrawCallと個数上限、更新時間を測る |
| DirectX12 | 描画追加時はDescriptor寿命、Resource Barrier、Fence完了前の解放/上書きを確認する |
| VRAM | 共通素材を再利用し、表示ごとのTexture/Buffer再作成を避ける |

現状は設計調査のみで、これらの実機安全性・性能を確認したわけではない。大きいSessionへ新しい処理をさらに直接詰め込むのではなく、状態変更を専用Systemに分けて接続する。今回のためだけの全体リファクタリングは行わない。

## F. 提出で見せる順番

1. 作物を育てる通常画面を見せる。
2. 予兆が出て、守る対象と期限が分かるところを見せる。
3. 駆除して被害を防ぐ。
4. 同条件で放置した場合との品質差を見せる。
5. 収穫記録・大会結果までつながることを見せる。

検証用の再現データを使う場合は、その旨を明記する。通常プレイの発生頻度や難度を検証した証拠と混同しない。
